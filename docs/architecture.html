Inspekt — Architecture Map

What lives where, how the three run-modes hang together, and how to tame the moving parts.

1. Top-level layout, at a glance

Three things cause most of the confusion, and they're worth naming up front:

  • inspekt/inspekt/ — the outer folder is the repo; the inner is the importable Python package. This is standard Python convention (same as requests/requests/), not a mistake.
  • desktop-vm/ — not the VM. It is a Tauri native shell that loads the VM's control panel over HTTP.
  • docker/browser-vm/ — this is the actual VM: a Docker image running Chromium + the extension + control panel.
  • inspekt/ repo root
    • inspekt/ python pkg the CLI, bridge, services, scripts (core product)
      • app/cli/ ~45 Click command modules (entry: inspekt = inspekt.app.cli:main)
      • app/api/ FastAPI surface for programmatic use
      • app/mcp/ MCP server exposing 33 tools to Claude Desktop
      • bridge_ws.py WebSocket server (browser ⇄ CLI message broker)
      • client.py BridgeClient — HTTP/socket client used by every CLI command
      • config.py get_bridge_port() — 8765 host, 8767 VM mode
      • core/ command registry, handlers, introspection
      • services/ ~79 modules: browser control, a11y, extraction, AI…
      • transport/ unix-socket + tcp fallback for bridge client
      • scripts/ 65+ JS files injected into the browser (DOM, axe, record, replay)
      • man/ pre-built man pages committed for the wheel
    • extensions/ browser ext WebExtension source (single source of truth)
      • chrome/ MV3 (service worker, DevTools panel, offscreen doc)
      • firefox/ MV2 (persistent background page)
      • shared/ permissions, websocket client, postMessage bridge
    • docker/ virtual machine the actual "VM" that runs everywhere
      • browser-vm/ Alpine + Chromium + noVNC + supervisord + control-panel.html + control/terminal/bridge servers
      • headless/ stripped-down variant (no noVNC) — looks orphaned
    • desktop-vm/ tauri shell native wrapper — NOT the VM, just a webview into it
      • src/ Svelte launcher (Docker check, starts VM, then opens main window)
      • src-tauri/ Rust shell; loads http://localhost:6080/control.html as external URL
      • src-tauri/capabilities/clipboard-remote.json critical — permissions for the remote VM URL
    • desktop-pdf/ tauri app separate PDF-report viewer; bolted on, not part of core flow
    • scripts/ build tools bundle-vm, watch-extensions, build_man, build_popover_css…
    • docs/ mkdocs
    • archive/ history old refactoring notes — could use a README or a cull
    • Makefile ~25 targets test/lint/typecheck, VM lifecycle, man-pages
    • package.json root bundle, build, preview, start, dev — wraps VM workflow
    • pyproject.toml py console script, deps, lint config

2. The three execution modes

Every mode ultimately routes through the same bridge (bridge_ws.py) and the same extension code (extensions/chrome/). What differs is where the browser runs and who drives commands.

Mode 1 — CLI + Local Browser

User installs extension in their Chrome/Firefox. CLI runs on host.

terminal └─ inspekt <cmd> └─ BridgeClient (HTTP) └─ bridge_ws.py :8765 └─ WebSocket → extension └─ MAIN-world JS → DOM
Ports: bridge 8765 only.
Start: inspekt start (daemon).

Mode 2 — Control Panel + VM

Browser inside Docker. User opens http://localhost:6080/ in any browser.

any browser → :6080 └─ control-panel.html └─ fetch :8888/inspekt/<cmd> └─ control-server.py └─ inspekt CLI (in container) └─ bridge_ws.py :8767 └─ WS → bundled extension └─ Chromium (via VNC)
Ports: noVNC 6080, control 8888, terminal 8889, bridge 8767, CDP 9222, mitm 8080.
Start: inspekt vm start.

Mode 3 — Tauri Desktop + VM

Identical to Mode 2 — Tauri is just a native window around the same URL.

Tauri launcher (Svelte :1421) └─ check_docker / start VM └─ opens main window → WKWebView loads :6080/control.html └─ (same stack as Mode 2) + __TAURI_INTERNALS__ (clipboard, drag, notify)
Extra plumbing: capabilities/clipboard-remote.json gates native APIs for the remote URL.
Start: cd desktop-vm && bun run dev.

3. Where does the extension live, and how does it stay in sync?

There is one source of truth — extensions/chrome/ and extensions/firefox/ — and three copies at runtime. Only the third (inside the Docker image) is automated; the others are manual.

5. What makes this confusing today

Name collision: desktop-vm/ vs docker/browser-vm/. The "desktop-vm" folder contains no VM; the Docker one does. New contributors regularly guess wrong.fix: rename desktop-vm/ → desktop/ (it's a Tauri shell)
Three npm/bun surfaces: root, desktop-vm/, desktop-pdf/. Each has its own bun.lock; none share scripts. "What do I run?" has different answers depending on which folder you happen to be in.fix: document the workflow at the root, or adopt a workspace (pnpm/bun workspace)
Control panel source ≠ what runs. Edits to docker/browser-vm/control-panel.html need make vm-bundle + make vm-restart to take effect. Forgetting either step silently shows stale UI.fix: let the container serve the un-bundled panel in dev mode
Extension manifest version drifts from pyproject.toml and desktop-vm/Cargo.toml. Four separate version fields with no single bump command.fix: one VERSION file + a bump script
Dockerfile does not run bundle-vm.mjs. The build expects dist/ to be pre-populated. A fresh clone + docker build ships stale assets.fix: add a pre-build step, or multi-stage build with a bun stage
docker/headless/ and archive/ are orphaned. No README, no current user, no decision recorded. They raise uncertainty about what's load-bearing.fix: add a one-line README in each; delete if confirmed dead
Two "bridges" share a name: bridge_ws.py (WS server) and shared/core/message-bridge.js (postMessage bridge). Grepping "bridge" conflates them.fix: rename in-extension one to dom-bridge.js / main-world-bridge.js
No "dev everything" command. Three terminals for a full round-trip: inspekt start, npm run watch:extensions, bun run tauri dev. No single entry point for a new contributor.fix: add make dev-all (overmind/foreman)

Coherence checks — "am I running the right bits together?"

NEWmake doctor — prints bridge port, VM container state, image SHA vs expected, extension version in container vs source, bundle dist mtime vs control-panel.html mtime. Surfaces "you forgot to bundle" before you see stale UI.
NEWmake verify-extension-sync — hashes extensions/chrome/ on host and inside the running container; exits non-zero if they differ. Perfect for a CI gate and for the dev-all loop.
NEWDockerfile runs bun scripts/bundle-vm.mjs in a builder stage, so docker build . from a clean clone produces correct assets without the user remembering.
NEWDev mode mounts extensions/chrome/ and docker/browser-vm/{js,css,control-panel.html} as volumes, so iteration loops are "save file → make sync-extension" with no rebuild.

8. Recommendations, ranked by payoff

  1. Ship a one-page "How the pieces fit" doc (this page, essentially) and link it from README.md. Most of the confusion is semantic, not structural.
  2. Rename desktop-vm/ → apps/desktop/ and docker/browser-vm/ → vm/. Biggest cognitive win, small code impact (git mv, update Dockerfile COPY paths, bundle-vm.mjs, Makefile targets, docs).
  3. Centralise versioning: a VERSION file plus make version NEW=… that rewrites every manifest. Kill the drift at its source.
  4. Fold bundle-vm.mjs into the Dockerfile (multi-stage build with a bun stage). Removes the silent-staleness failure mode.
  5. Add make dev-all with overmind/foreman. First-day-contributor experience becomes one command.
  6. Add make doctor and make sync-extension. These pay for themselves the first time someone debugs stale UI.
  7. Dispose of docker/headless/ and annotate archive/. Reduces "is this load-bearing?" anxiety.
